## 1. 范围 (Scope)

### 1.1 文档目的

本标准说明书规定「AI 健康伴侣」系统（以下简称"本系统"）的目标架构（Target Architecture），涵盖业务、数据、应用、技术、安全与合规五个架构域，并定义架构原则、服务质量需求与架构治理机制。本文件作为系统设计、开发实施、测试验收与后续演进的架构基线（Architecture Baseline）。

### 1.2 系统边界

本系统为面向个人消费端（C 端）的 AI+健康管理应用，聚焦两大核心场景：

- **饮食健康**：拍照识食、语音/文字记录、AI 能量与营养素分析、"七大要素"质感饮食诊断、营养缺口跨餐记账；
- **睡眠健康**：穿戴设备睡眠数据同步、睡眠评分与结构分析、AI 归因、睡前干预与晨间"防亏空"保护。

系统由三个 AI Agent（营养师 Agent、睡眠教练 Agent、健康管家 Agent）驱动，形成"无感采集 → 智能评估 → 最小可执行微行为 → 形成正循环"的业务闭环，并通过手机推送、锁屏 Rich Notification 全天候触达用户。穿戴设备（手表/手环）通知通道为后期开发项，本文件在其架构位置予以预留。

### 1.3 系统边界之外 (Out of Scope)

以下内容不属于本系统架构范围：

- 医疗器械级诊断、治疗方案制定与处方行为（本系统仅提供健康生活方式建议，医疗建议须附免责声明并引导就医）；
- 医疗机构信息系统集成与电子健康档案（EHR）交换（预留接口但不承诺互操作）；
- 企业级健康管理（B 端团体采购）多租户管理平面；
- 离线数据交易、数据捐赠与第三方数据商业化。

## 3. 术语和定义 (Terms and Definitions)

下列术语和定义适用于本文件。采用 ISO 规范术语风格，消除国际团队协作歧义。

### 3.1 能量分析 (Energy Analysis)

对用户单餐或单日所摄入食物，从**总热量**、**宏量营养素配比**（碳水/蛋白质/脂肪）、**膳食纤维**、**进食时序**（用餐时刻与结构）四个维度进行的定量与定性综合评估。本系统中的能量分析区别于单纯卡路里记账：其输出应(shall)包含"能量画像 + 缺口识别 + 归因解释 + 行动建议"四要素。

### 3.2 最小可执行微行为 (Minimum Viable Micro-Behavior, MVMB)

由 AI Agent 生成、面向用户当日执行的最小粒度健康干预动作。其应(shall)满足：可单次完成（3–20 分钟）、无需额外工具、结果可量化反馈、低心理负担（如"午餐补蛋白 30g""久坐 1 小时起身拉伸 2 分钟""饭后散步 10 分钟"）。MVMB 是"零焦虑"理念在干预层的落地载体，替代强制性、惩罚性的健康约束。

### 3.3 健康闭环 (Health Closed-Loop)

数据从采集到价值回流的状态机链路：**采集 → 分析 → 结论 → 建议 → 干预 → 反馈 → 记忆更新**。本系统要求任何一条记录不得为"孤岛数据"——每条记录应有(shall)AI 处理痕迹，每条建议应(shall)可追踪至用户反馈或干预结果（SRS 第 3.2 节）。

### 3.4 身体电量 (Body Battery)

基于睡眠时长/结构、HRV（心率变异性）与疲劳度综合计算，表征用户当前精力储备水平的 0–100 归一化指标。其阈值语义应(shall)明确：≥80% 为"活力充足"，<50% 触发"防亏空保护"（自动降级高强度安排为恢复性微行为）。该指标为晨间唤醒、运动护栏等子系统的决策输入。

### 3.5 全天候陪伴 (24/7 Companionship)

本系统按用户生理节律（晨间唤醒/餐前/久坐/午后低谷/睡前）全天候主动触达的 Agent 陪伴机制。其核心特征：主动（Agent 先行而非用户驱动）、节律对齐（干预时点贴合生理窗口）、柔性（附最小补救动作、可一键跳过、可免打扰）。该概念指导通知系统与节律任务（RoutineTask）的设计。

### 3.6 功能需求标识符 (FR Identifier)

本系统需求唯一标识，格式为 `FR-[模块]-[序号]`（如 FR-DIET-11），模块代码：AUTH（用户）、DASH（总览）、DIET（饮食）、SLEEP（睡眠）、NOTIFY（通知）、RHYTHM（节律）、AGENT（Agent）、NTF（通知细节）、DATA（数据）。本文件通过 FR 标识符与 SRS 建立可追溯映射。

## 4. 架构原则 (Architectural Principles)

原则按 TOGAF 原则模板定义（陈述 / 理由 / 影响）。每条原则对系统设计具有强制指导作用。

### 4.1 业务原则

**P-01 闭环优先 (Closed-Loop First)**
- 陈述：任何业务能力不得以"孤立数据展示"为终态，必须(shall)纳入采集→分析→建议→干预→反馈闭环。
- 理由：本系统差异化在于 Agent 驱动的功能闭环；孤岛数据违背产品定位。
- 影响：服务间调用链路须保留反馈通道；数据模型须支持任务状态机与事件溯源。

**P-02 零焦虑体验 (Zero-Anxiety by Design)**
- 陈述：面向用户的呈现与干预策略宜(should)采用"质量诊断 + 模糊区间"替代"精确扣减 + 惩罚性提示"。
- 理由：降低卡路里焦虑是产品理念，直接影响留存与口碑。
- 影响：AI 输出层应有(shall)文案规范层（柔性语气、免打扰等级）；营养计算保留精确视图但不作为默认呈现。

**P-03 隐私默认保护 (Privacy by Default)**
- 陈述：系统对健康数据应(shall)默认采用最小化采集与本地优先存储，云端仅存脱敏统计。
- 理由：健康数据属敏感个人信息，PIPL/GB/T 35273 强制要求；隐私是信任前提。
- 影响：数据架构须支持"本地优先 + 云端同步"双模；原始照片与健康明细默认不上云（SRS FR-DATA-02）。

### 4.2 架构原则

**P-04 松耦合与领域化 (Loose Coupling & Domain Orientation)**
- 陈述：系统应(shall)按业务领域划分服务边界（饮食/睡眠/通知/Agent/用户），服务间通过版本化 API 交互，禁止共享数据库直连。
- 理由：独立演进、故障隔离、团队自治，符合微服务架构实践。
- 影响：每个服务拥有独立数据存储；跨服务事务采用 Saga/事件补偿；契约经 OpenAPI 管理。

**P-05 标准化接口 (Standardized Interfaces)**
- 陈述：所有对外能力应(shall)经 API 网关发布，遵循统一鉴权、限流、可观测规范；接口版本化 `/v1/`。
- 理由：统一安全与治理边界，支持多端（App/穿戴/Widget）复用。
- 影响：禁止服务绕过网关直连；健康数据接口须设备级校验（SRS 8.2）。

**P-06 无状态与可水平扩展 (Stateless & Horizontally Scalable)**
- 陈述：核心服务实例应(shall)无状态化，会话状态外置于分布式缓存/存储；任何服务可通过增加实例水平扩展。
- 理由：满足 100 万注册用户、峰值 5 万 QPS 的容量目标（SRS NFR-PERF-05）。
- 影响：禁止实例本地持久化；WebSocket 会话采用粘性会话 + 状态外置或网关代理方案。

**P-07 安全前置 (Security by Design)**
- 陈述：安全控制应(shall)在架构设计阶段前置规划，贯穿开发全生命周期（Shift-Left）；默认拒绝（Deny by Default）。
- 理由：健康数据泄露风险高，等保二级起步、目标向三级演进。
- 影响：威胁建模进入每个功能评审；安全基线、密钥管理、审计日志为架构强制组件（见 5.5）。

**P-08 可观测性内生 (Observability Built-in)**
- 陈述：每个服务应(shall)输出结构化日志、指标与链路追踪，支持全链路问题定位与业务转化分析。
- 理由：Agent 编排链路复杂（多 Agent 协作 + 通知闭环），无观测则无法运营。
- 影响：统一日志格式与 Trace ID 透传；通知送达/点击埋点纳入指标体系（SRS FR-NTF-07）。

**P-09 可演进与云中立 (Evolvability & Cloud-Neutral)**
- 陈述：技术选型应(shall)避免厂商锁定，优先开源与标准协议；云部署宜(should)支持多公有云（阿里云/腾讯云/AWS）。
- 理由：满足多地域合规（数据本地化）与成本谈判能力。
- 影响：容器化 + Kubernetes 作为部署标准；对象存储与消息队列选择兼容性强的实现。
