    技术架构书¶

    Technical Architecture Document¶

    项目 内容
    文档编号 TAD-AIH-2026-001
    版本 V1.0
    编写日期 2026-08-09
    文档状态 评审稿
    关联文档 《国际标准架构标准说明书》(ISA-AIH-2026-001)、《架构图集》(ADS-AIH-2026-001)、《软件需求规格说明书 V1.1》(SRS-AIH-2026-001)

    本文件规定「AI 健康伴侣」的技术选型、服务设计、部署方案与运维体系，是研发实施的技术依据。规范用语：应(shall) / 宜(should) / 可(may)。

    1. 技术选型总览 (Technology Stack)¶

    1.1 技术选型决策矩阵¶

    层 技术 版本基线 决策理由 备选方案
    客户端 iOS SwiftUI iOS 16+ 声明式 UI、跨设备（iPhone/Watch）代码共享 UIKit 混合
    客户端 Android Kotlin + Jetpack Compose Android 10+ (API 29+) 现代 UI 工具包、Kotlin 协程 Flutter（放弃：健康权限原生集成成本高）
    服务端语言 Go Go 1.22+ 高并发（5 万 QPS 目标）、低延迟、部署简单 Java/Spring Boot（备选：复杂事务域）
    Agent/AI 服务 Python 3.11+ LLM 生态（LangGraph/语义内核）、科学计算 Node.js
    API 网关 APISIX / Kong 3.x 云中立、插件丰富（限流/鉴权/灰度） Nginx + Lua
    数据库（OLTP） PostgreSQL 15+ 关系模型 + JSONB + pgvector 向量扩展一体化 MySQL 8
    缓存/会话 Redis 7.x 会话/限流/热数据/锁 —
    消息总线 Apache Kafka 3.x 事件驱动闭环、削峰、回溯 RocketMQ
    向量检索 pgvector（起步）→ Milvus（规模化） 2.x 起步共用 PostgreSQL，规模化独立 Elasticsearch kNN
    分析数仓 ClickHouse 23.x 高吞吐写入、OLAP 聚合查询（能量趋势/报告） StarRocks
    对象存储 云 OSS/S3 — 照片/报告/分享卡片 兼容 S3 即可
    编排调度 Kubernetes 1.29+ 容器化标准、自愈、滚动发布 云托管 EKS/ACK
    可观测性 OpenTelemetry + Prometheus + Grafana + Loki + Jaeger — 指标/日志/追踪全链路统一 SkyWalking
    CI/CD GitLab CI / GitHub Actions + ArgoCD — 声明式 GitOps 部署 Jenkins

    1.2 决策原则（映射 ISA P-04/P-06/P-09）¶

    1. 服务端默认 Go：核心业务服务（用户/饮食/睡眠/通知/节律）均采用 Go，保证运行时一致性与协作效率；
    2. Agent 层 Python：仅 AI 编排/视觉/RAG 服务采用 Python，与 Go 服务经版本化 API + 事件隔离；
    3. 数据库统一 PostgreSQL：起步期单实例多库（逻辑隔离），避免过早引入多种数据库运维负担；规模化后按服务拆分实例；
    4. 云中立：全部选型优先开源/标准协议实现，可在阿里云/腾讯云/AWS 任一平台运行（ISA P-09）。

    2. 客户端架构 (Client Architecture)¶

    2.1 iOS 客户端¶

    模块 技术 说明
    UI 层 SwiftUI + Combine 15 个页面视图（Dashboard/饮食/睡眠/Agent 对话/通知/我的）
    本地存储 SwiftData + Keychain 健康明细本地优先（FR-DATA-02）；密钥入 Keychain
    健康数据 HealthKit 步数/心率/睡眠/体重读入（需用户授权）
    通知 UserNotifications + WidgetKit 锁屏 Rich Notification 与快捷动作（FR-NOTIFY-03/04）；Widget 常驻能量概览
    网络 URLSession + Async/Await HTTPS + TLS 1.3；请求签名与幂等键
    照片 Vision + 相机框架 拍照识食前处理（方向校正/压缩 ≤2MB）

    2.2 Android 客户端¶

    模块 技术 说明
    UI 层 Jetpack Compose Material 3、深色模式适配
    本地存储 Room + DataStore + Keystore 本地优先；密钥入 Android Keystore
    健康数据 Health Connect (API 1+) 步数/心率/睡眠读入
    通知 FCM + NotificationManager 锁屏通知渲染一致性
    网络 Retrofit + OkHttp + Coroutines 统一拦截器（鉴权/日志/重试）

    2.3 客户端-服务端契约¶

    • RESTful + WebSocket，版本化 /v1/（ISA P-05）；
    • 接口契约以 OpenAPI 3.x 管理，客户端自动生成类型安全 SDK；
    • 幂等设计：记录提交携带幂等键 Idempotency-Key，防重复提交（SRS 8.2）；
    • 离线能力：核心记录（拍照/语音/快捷录入）支持离线队列，联网后同步（NFR-PERF-06）。

    3. 服务端微服务设计 (Server Microservices)¶

    3.1 服务清单¶

    服务 职责 语言 数据存储 关键需求映射
    user-service 注册登录、个人档案（身高/体重/目标/BMR）、订阅 Go PG: user schema FR-AUTH-01~04
    diet-service 食物记录、能量分析结果存储、食物库检索、扫码 Go PG: diet schema + 食物库 FR-DIET-01~16
    sleep-service 睡眠数据同步、评分、结构、归因存储 Go PG: sleep schema FR-SLEEP-01~11
    notify-service 通知编排（事件→模板→通道→投放→去重）、推送接入 Go PG + Redis FR-NOTIFY-01~09 / FR-NTF-01~07
    rhythm-service 节律任务调度（晨间/餐前/久坐/午后/睡前）、免打扰 Go PG + Redis（定时任务） FR-RHYTHM-01~08
    archive-service 起居注汇总、饮食档案、勋章/Streak Go PG: archive schema FR-DASH-08/09
    agent-orchestrator 健康管家 Agent 编排（Python）、工具调用、记忆 Python PG + pgvector FR-AGENT-01~10
    vision-service 食物视觉识别、份量估算 Python 对象存储 FR-DIET-01
    payment-service 订阅支付回调、订单 Go PG: pay schema 订阅（后期）

    3.2 服务边界规则¶

    1. 每个服务拥有独立数据库 Schema/实例，禁止跨服务直查数据库（ISA P-04）；
    2. 服务间同步调用经内部 HTTP/mTLS，异步经 Kafka 领域事件；
    3. 领域事件命名规范：{domain}.{action}（如 food.recorded、sleep.synced、task.feedback、notify.sent）；
    4. 跨服务一致性采用 Saga 编排 + 事件补偿；支付域允许 TCC 强一致（受限范围）。

    3.3 核心 API 设计¶

    资源 方法 路径 说明
    饮食记录 POST /v1/meals 幂等键；拍照/语音/文字 3 种来源
    饮食分析 GET /v1/meals/{id}/analysis 能量画像 + 七大要素诊断
    睡眠同步 POST /v1/sleep/sessions 穿戴同步或手动
    任务 PATCH /v1/tasks/{id} 完成/忽略/纠正（闭环反馈）
    Agent 对话 WS /v1/agent/chat 流式输出
    通知设置 PUT /v1/notify/preferences 免打扰三级控制

    统一响应结构：

    { "code": 0, "msg": "ok", "data": {...}, "traceId": "..." }

    错误码段位：0 成功；10xxx 客户端参数；20xxx 鉴权；30xxx 限流/配额；40xxx 服务端；50xxx 外部依赖（LLM/推送）。

    4. 数据架构 (Data Architecture)¶

    4.1 数据库设计¶

    库/Schema 服务 核心表 说明
    user user-service users, user_profiles, subscriptions, user_preferences 档案含 BMR 计算所需字段
    diet diet-service food_records, meal_analyses, food_items, factor_analyses, water_logs 照片 metadata 入 PG，原始文件入对象存储
    sleep sleep-service sleep_sessions, sleep_analyses 结构数据（深/浅/REM/清醒）
    notify notify-service notifications, notification_templates, channel_prefs 送达/点击埋点
    rhythm rhythm-service routine_tasks, dnd_windows 定时任务状态
    archive archive-service living_archives, badges, streaks 每日汇总
    agent agent-orchestrator agent_tasks, agent_memories, feedback_logs agent_tasks 为闭环状态机主表

    索引与容量（按 100 万注册用户规划）：

    指标 规划值
    每日活跃记录 ~500 万条（饮食+睡眠）
    单表日增 food_records ~100 万
    数据保留 原始照片 90 天；分析结果永久（脱敏）
    分片策略 起步单库；规模化按 user_id 哈希分片（shard key = user_id % N）

    4.2 数据生命周期¶

    1. 采集：客户端本地加密 → 脱敏结构化数据上云（TLS 1.3）；
    2. 存储：热数据 PG（90 天）→ 冷数据归档对象存储（分析结果）→ 数仓 ClickHouse（聚合指标）；
    3. 删除：注销 30 天内全链路删除（含备份清理），密钥级联销毁；
    4. 导出：用户数据导出 JSON/CSV/PDF（FR-DATA-03）。

    4.3 数据主权与合规¶

    • 中国区数据境内存储（PIPL/数据安全法）；跨境传输需安全评估；
    • 健康数据按敏感个人信息分类：默认最小化、单独同意、本地优先；
    • 大模型输入脱敏管线（姓名/手机号/定位替换），输出合规审核（生成式 AI 办法）。

    5.2 关键设计决策¶

    决策点 方案 理由
    编排框架 LangGraph（Python） 多 Agent 图式编排、状态持久化、可观测
    模型路由 按任务分级：分类/抽取用快模型，深度分析用主模型 成本控制（AI 配额按天/用户）
    工具调用 结构化 JSON 工具契约 + JSON Schema 校验 Agent 输出可执行化（FR-AGENT-05）
    记忆体系 短期（近期行为窗口）+ 长期（偏好/忌口 RAG 向量化） FR-AGENT-03；用户可删除记忆
    延迟目标 分析 P95 ≤ 5s；任务生成 P95 ≤ 8s（FR-AGENT-10） 流式输出 + 缓存 + 模型分级
    降级策略 主模型不可用时降级快模型 + 模板兜底；视觉失败转文字录入 保证闭环可用性

    5.3 视觉识别管线（拍照识食）¶

    1. 客户端预压缩（≤2MB）→ 上传临时桶；
    2. vision-service 检测+分类（食物类别）→ 份量估算（分割+体积模型）；
    3. 关联食物库（≥10 万条）匹配营养数据；
    4. 结果结构化返回 → 用户确认/修正份量 → 落库；
    5. 准确率目标：识别 ≥90%，份量误差 ≤30%（SRS 10.1 验收项）。

    5.4 Agent 记忆与隐私¶

    • 记忆默认仅存结构化向量摘要（不存原始照片/身份标识）；
    • 用户可查看/删除记忆（FR-AGENT-03），删除即级联清除向量与备份；
    • 不使用用户健康数据训练第三方模型（NFR-SEC）。

    6. 部署与高可用 (Deployment & HA)¶

    6.1 部署拓扑（三阶段）¶

    阶段 拓扑 可用性 适用期
    L1 MVP 单云双可用区：K8s 双节点池 + PG 主备同步复制 + Redis 主备 + Kafka 双副本 99.9% 上线 ~10 万用户
    L2 规模化 双云双可用区 + 读写分离 + 队列分区扩容 + 缓存集群 99.95% 10 万 ~ 50 万用户
    L3 多活 跨地域双活：写入按用户拆分 + 数据双向复制 + 就近接入 99.99% 50 万+ / 海外市场

    6.2 容器与编排¶

    • 全部服务容器化（多阶段构建，镜像 ≤300MB）；
    • K8s 声明式部署（Helm Chart + ArgoCD GitOps）；
    • HPA 自动扩缩容（CPU 70% / QPS 阈值双指标）；
    • 滚动发布 + 金丝雀灰度（5%→25%→100%），可一键回滚（NFR-AVAIL-04）。

    6.3 容灾指标¶

    指标 目标 实现方式
    RPO ≤5min（同城），≤15min（跨地域） 同步复制（同城）/ 异步复制（跨地域）
    RTO ≤1h PG 自动故障转移 + 灾备可拉起
    备份 每日全量 + PITR 增量 PG Base Backup + WAL 归档至对象存储

    6.4 容量规划（100 万注册 / 5 万峰值 QPS）¶

    组件 规划
    业务服务 核心服务 6~12 Pod × 2AZ，HPA 上限 ×4
    PostgreSQL 4C16G ×2（主备）+ 连接池 PgBouncer
    Redis 集群模式 6 节点（缓存/限流/会话）
    Kafka 3 broker 起步，分区 = 消费者组 ×4
    ClickHouse 2 节点，保留 180 天聚合指标

    7. 安全与合规实现 (Security & Compliance Implementation)¶

    7.1 身份认证与授权¶

    1. 登录：手机号验证码（短信）/ 邮箱 + 微信/Apple/Google OIDC（FR-AUTH-01）；
    2. 令牌：Access Token (JWT, ≤15min) + Refresh Token（轮换+吊销）；刷新令牌设备绑定；
    3. 健康数据访问：设备级校验（App 实例标识 + 令牌绑定），防止令牌被盗用跨设备访问（SRS 8.2）；
    4. RBAC：用户/访客/管理员三角色；管理端二次认证。

    7.2 加密标准¶

    场景 标准 说明
    传输 TLS 1.3（RFC 8446） 全链路强制，禁用 TLS <1.2
    静态数据 AES-256-GCM 敏感字段列级加密；密钥 KMS 托管
    本地存储 iOS Keychain / Android Keystore 生物识别解锁可选项
    令牌签名 EdDSA (Ed25519) / RS256 JWT 签名
    哈希 Argon2id 密码等凭据（本系统以验证码为主）

    7.3 零信任实践¶

    • 网络层：服务间 mTLS（服务网格/边车），默认拒绝未授权内网调用；
    • 身份层：每请求鉴权 + 设备指纹校验；
    • 数据层：列级加密 + 行级访问控制（RBAC2，用户数据按 user_id 隔离）；
    • 持续验证：异常行为检测（异地登录/高频 AI 调用/批量导出）触发风控。

    7.4 AI 合规护栏（GUARD）¶

    1. 输入脱敏：LLM 请求前去除姓名/手机号/精确地理位置/设备标识；
    2. 输出审核：内容安全审核（政治敏感/医疗夸大/焦虑制造文案拦截）；
    3. 风险护栏：极端饮食/厌食倾向/疾病咨询 → 免责声明 + 引导就医（FR-AGENT-07）；
    4. 备案：生成式 AI 服务依《生成式人工智能服务管理暂行办法》备案；大模型供应商合规评估。

    7.5 审计与日志¶

    • 全量操作审计（登录/数据导出/删除/权限变更）入不可篡改日志；
    • 日志落盘前脱敏（手机号/身份证/健康数值）；
    • 季度渗透测试 + 漏洞扫描；年度等保测评（二级起步）。

    8.1 三支柱实现¶

    SLO 目标 监控点

    8.3 告警分级¶

    • P0 严重（服务宕机/数据丢失风险）：立即电话+群告警，15min 响应；
    • P1 高（SLO 逼近/队列积压）：30min 响应；
    • P2 中（单实例异常/延迟劣化）：工作日当日处理；
    • 告警疲劳控制：抑制规则 + 聚合窗口 + 值班轮换。
